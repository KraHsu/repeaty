# M0 文件保存与恢复原型

日期：2026-10-25。实现位于 [`crates/workspace-store`](../crates/workspace-store/README.md)，上层约定见 [内容格式与外部编辑](WORKSPACE_CONTENT_FORMAT.md#6-repeaty-内部编辑冲突与中断)。

本批验证单个 Markdown 工作文件、独立内容对象与 SQLite 记录之间的保存。原型只能创建空的实验目录，或打开带专用标记及数据库身份的实验目录；没有接入 Tauri、服务端、现有学习库或迁移入口。

## 文件与数据库的职责

```text
临时实验目录/
├── prototype.json                 # M0 实验标记，不是正式 workspace.json
├── prototype.lock                 # 配合应用写入者之间的锁
├── state.prototype.sqlite3        # 最小接受状态、卡片、草稿预约与操作回执
├── notes/old.md                   # 可被外部编辑的工作文件
└── .repeaty/
    ├── objects/sha256/ab/<hash>    # 单独复制的正文对象，不与工作文件硬链接
    └── transactions/<operation>/
        ├── intent.json            # 冻结身份、基线、目标摘要、新卡映射与替换方法
        ├── slot                   # 发布前为新内容；Unix 交换后为实际旧文件
        ├── displaced              # Windows 的旧文件保留位置
        ├── publish-started        # 持久记录发布尝试即将开始
        ├── published              # 原生操作成功且完成本平台的同步后记录
        ├── complete               # SQLite 接受已提交的完成记录
        └── attention-<hash>.json   # 追加的待处理证据，不覆盖更早记录
```

SQL 表只表达这次实验需要的最小状态，不是已经定稿的工作目录 schema。`application_id = 0x52504d30`（RPM0）、`user_version = 1001` 与专用文件名用于隔离实验；不升级已有库，不把它当作正式 RPTY 格式。Rust crate 沿用产品版本 0.27.0，并纳入现有版本一致性检查，不单独发布产品。

工作文件保留当前写入内容，SQLite 保存已接受版本，内容对象保存精确字节。编辑不更新旧卡的调度 JSON；新卡映射由调用方预先生成并冻结，协调器不运行 FSRS，也不重放评分。

## 一次保存

1. 验证请求和路径，持久保存新正文对象。原型只接受 UTF-8 文本及受限的 `notes/<文件名>.md` 路径；正文与序列化意图均限制为 2 MiB，避免产生恢复器无法读取的日志。
2. 单独复制发布候选，写入 `intent.json`。操作 ID、Note ID、预期旧摘要、新摘要、新卡 ID 与草稿归属随后不能用另一份请求替换。
3. 在 SQLite 中预约本次操作及草稿的正式身份。同一草稿不能被另一操作或另一个 Note ID 再次确认。预约不等于消费草稿。
4. 核对数据库接受基线与当前文件，记录 `publish-started`，调用保留旧文件的原生替换；新文件使用禁止覆盖目标的发布方式。正文未变时不交换工作文件。
5. 核对实际旧文件和新工作文件。实际旧字节不符合基线，或工作文件已被外部修改 / 删除时，保留所有文件与对象，进入待处理。
6. 在一个 SQLite 事务内提交 Note 接受版本、新卡映射、草稿消费、变更记录及操作回执；任何约束或基线检查失败都一起回滚。
7. 提交后记录 `complete`。重试优先读取原操作回执，不再次创建卡片或消费草稿。

工作文件发布与 SQLite 提交仍不是一个原子事务。它们之间的间隙由可检查的日志和内容对象覆盖，不能描述成「SQLite 锁住了外部编辑器」。

## 原生替换与竞争

| 平台    | 修改已有文件                                         | 新建文件                     | 同步覆盖                       |
| ------- | ---------------------------------------------------- | ---------------------------- | ------------------------------ |
| Linux   | `renameat2(RENAME_EXCHANGE)`，候选路径保留实际旧文件 | `RENAME_NOREPLACE`           | 文件与目录同步                 |
| macOS   | `renamex_np(RENAME_SWAP)`，候选路径保留实际旧文件    | `RENAME_EXCL`                | 文件与目录同步                 |
| Windows | `ReplaceFileW`，始终提供旧文件保留路径               | 不带覆盖标志的 `MoveFileExW` | 文件同步；未证明目录掉电持久性 |

这些方法保留替换当时的实际文件，不能提供与任意编辑器之间的强比较交换。替换前后都可能有外部写入，包括写后又复原的 ABA。

发现替换前最后一刻的竞争时，工作路径可能已经是应用候选，外部版本保留在事务目录。原型不会自动交换回去，因为第三个写入者可能已经修改了当前工作文件。后续界面需展示并处理这些版本；本批没有实现冲突选择 UI。

编辑器仍持有旧句柄时，后续写入会落到保留路径。原型保留该文件并在恢复时重新核对，把检测到的新字节另存为内容对象；旧的历史对象不变。因此事务目录中的旧文件不是已完成后可立即删除的缓存。本批没有实现它们的垃圾回收，也不以两次摘要相同为理由宣称编辑器已经停止写入。

不支持的原语、目标名已被占用或原生调用失败时，不退回普通覆盖。Windows 可能出现部分完成的替换错误，因此失败后保留候选、旧路径和日志，不猜测文件未动，也不自动再调用一次。

## 中断后如何处理

| 恢复时的证据                                   | 处理                                                         |
| ---------------------------------------------- | ------------------------------------------------------------ |
| 只有新内容对象，或意图尚未登记                 | 保留材料，显示未完成准备；明确重试可沿用同一身份继续准备     |
| 已预约，发布尚未开始                           | 不自动写文件；明确重试可继续同一次操作                       |
| 已记录发布尝试，但文件拓扑不能证明结果         | 保留待处理状态；即使重试也不再次交换文件                     |
| 新文件与保留旧文件能证明已发布，数据库尚未提交 | 验证对象、基线与草稿预约后补完同一 SQLite 接受事务           |
| SQLite 已提交，完成标记缺失                    | 读取原回执，补记完成；不重复建卡或写变更记录                 |
| 工作文件又被编辑 / 删除                        | 保留外部结果，显示待处理；不拿数据库中的旧字节覆盖工作路径   |
| 提交后旧句柄又写入                             | 保留新写入与已提交回执；接受状态不回滚，后续版本交由用户处理 |
| 日志、对象或关联记录损坏 / 缺失                | 阻止自动接受，报告待处理；已有提交回执不会被误报为回滚       |

`Attention.committed` 区分已知提交、已知未提交与无法确认，避免用一个普通错误提示推断草稿是否被消费。较早操作的回执不会把后续合法保存回退到旧接受版本。

## 验证

```bash
cargo fmt --manifest-path crates/workspace-store/Cargo.toml --check
cargo clippy --manifest-path crates/workspace-store/Cargo.toml --locked --all-targets -- -D warnings
cargo test --manifest-path crates/workspace-store/Cargo.toml --locked
```

本地 Linux：29 项测试通过。其中一个测试驱动 18 次独立子进程退出，覆盖编辑与草稿确认各 9 个检查点：正文对象、意图、预约、发布尝试、文件发布、发布记录、SQLite 提交前、提交后及完成记录。子进程直接退出，不依靠正常析构来回滚。

后续 CI 在 macOS 发现重开偶发报已打开：并行生成的子进程可以继承锁的文件描述符，单纯关闭父进程描述符不足以立即解锁。现已增加持有继承描述符的确定性回归样例：修复前在 Linux 也能稳定复现；修复后在 SQLite 连接关闭后显式解锁，再关闭自身描述符，仍阻止同时打开第二个写入者。本地原型测试增至 30 项，跨平台结果按后续批次重新记录。

同时覆盖：原 ID 与调度 JSON 保留、重复恢复、复制操作 ID、草稿重复确认、原生发布竞争、旧句柄迟到写入、新文件名冲突、损坏对象 / 日志、卡片约束失败、SQLite 基线变化，以及可检测的符号链接 / 硬链接输入。每次中断恢复后检查数据库完整性和变更记录数量。

提交 `31dffc5` 的三平台原型 CI 均已通过，并上传测试日志：[Linux](https://github.com/KraHsu/repeaty/actions/runs/40207103311/job/121210418937)、[Windows](https://github.com/KraHsu/repeaty/actions/runs/40207103311/job/121210419025)、[macOS](https://github.com/KraHsu/repeaty/actions/runs/40207103311/job/121210419108)。Linux / macOS 为 29 项，Windows 为 27 项；差别来自仅在 Unix 运行的两项链接检查，三平台都执行了 18 个子进程中断场景。这是原语与最小协议的执行证据，不是三平台客户端 / 编辑器的正式目录验收。

## 尚未覆盖

- 真实 Markdown / 引用校验与 Rust 协调器的对接；变体退役、来源版本与学习历史的完整持久结构。
- 带媒体的多文件发布、真实 MCP 草稿确认、草稿附件、检查点恢复和旧库迁移。
- 任意嵌套 / Unicode 路径、长期文件监听、权限变化、对抗目录替换的句柄相对访问与完整冲突解决。
- 实际编辑器 GUI 的保存方式、磁盘写满、文件系统 / 网络盘矩阵、硬断电与设备缓存行为。

当前原型使用私有、固定的实验目录，逐段拒绝可检测的目录链接，但路径检查本身不构成对抗任意并发目录替换的安全边界。进程退出样例也不能代替断电验证，不能因此直接打开正式目录写入。
