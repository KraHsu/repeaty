# 练习历史性能

[开发文档](DEVELOPMENT.md#大数据量存储) · [LeetCode 使用](LEETCODE.md)

## 测量范围

`npm run benchmark -- --history --runs 3` 在独立 Chromium 上下文中建立 10,000 张卡、100,000 条复习记录、20,000 次练习和 60,000 次提交。每份代码 2,048 字符，每题含约 2 KB 的原始题面。数据只写入随机命名的临时 IndexedDB，完成后删除。

每轮先造数并保存，随后重载页面，释放造数阶段的对象，再测重新读取、历史视图、筛选、展开代码、提交状态保存、评分和备份。输出包含每轮数据、数值中位数、CPU、系统、Node 与浏览器版本。可用 `--output /tmp/history.json` 指定结果位置，默认写入 `test-results/history-benchmark.json`。

`loadMs` 从读取数据库计时到建立内存索引，包含自动快照检查；它不包含下载应用、启动浏览器或加载字体。`loadedHeapMiB` 在读取后、挂载历史视图前主动回收垃圾再取 Chromium 的 JS 堆使用量；它不代表进程总内存，也不能直接用于推断 WebKit 或系统安装包的内存。

历史视图挂载和筛选耗时包含 Vue 更新与两帧绘制等待。导出写入流式接收器，包含读取、序列化与 ZIP 压缩，不包含系统保存对话框或磁盘写入。代码使用重复文本，因此压缩率与耗时只适合比较同一份基准。

优化后三轮的 JS 堆采样为 139–143 MiB，本文采用中位数并保留全部原始样本。历史视图在基准页单独挂载，挂载与筛选耗时不代表整页导航。

这是本机测量，不能当作低配设备的性能保证。初次批量保存会额外维护摘要索引；导出则分批取回完整代码，交换的是平时的内存占用与导入、导出时的工作量。自动快照仍使用修订号和变更日志，不复制全库。

另用原有的普通卡基准补测一次：1 万张卡、10 万条复习记录，评分总耗时为 29.4 → 25.1 ms。它只用于检查基础评分路径，单轮结果不作为性能保证；原始值同样保留在结果文件中。

## 存储与兼容

IndexedDB 从 v6 升为 v7，新增 `attemptSummaries` 派生索引，原始提交仍在 `attempts`。首次升级需要扫描既有提交建立摘要；升级事务完成前不切换新库。提交、摘要与修订号一起提交或回滚，删除和恢复快照也同时维护两处记录。

运行时 `Library.attempts` 可以是 `AttemptRecord` 摘要，完整提交由 `getAttempt` 读取。读取检查修订号与记录身份，组件卸载、切换记录或收起时丢弃正文；读取失败可以重试。查看答案状态只在正文读取成功后更新。

API v3 增加可选 `historyVersion: 1` 能力。支持的服务提供 `GET /library/summary` 与 `POST /library/attempts`，后者按编号或位置读取完整记录。两者沿用账户与 `X-Repeaty-User` 校验；正文还必须匹配请求中的库修订号。批量读取最多 128 条，服务端按约 4 MiB 原始 JSON 限制批次。本地同样按 128 条读取。旧 API v3 服务继续通过原接口读取完整库。

学习数据仍为 v5、SQLite schema 为 v2、`.repeaty` 容器为 v2。备份不保存摘要代替正文：流式导出会核对每批的修订号、顺序和数量，正文不完整或库发生变化时中止。旧 JSON 导出和快照恢复按需读入完整记录，仍受原有容量限制。

## 后续边界

启动仍读取笔记题面、练习快照、调度状态和提交摘要，搜索与历史分页使用这些内存索引。SQLite 的摘要查询也仍需投影原记录。本轮按需读取的范围是提交代码与裁判详情；更多题面、历史或账户数据仍可能增加启动成本。

本基准没有媒体，不测网络延迟、三平台安装包启动时间或 Today 查询 P95。媒体和长文本使用独立的 128 MiB 浏览器往返测试；快照、旧库升级、完整正文导出、账户隔离与读取失败另有回归测试。
