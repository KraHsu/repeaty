# 完整工作目录备份与恢复

桌面“数据与备份”中的完整备份使用 `.repeaty-workspace` 文件。它与 `.repeaty` / JSON 整库学习数据备份、学习库内检查点是不同的入口：完整备份用于在新目录中还原整个工作目录；`.repeaty` / JSON 恢复会替换当前学习数据，并保留备份中的个人学习进度。这些备份都不是单卡组或所选资料的分享包。资料导出和卡片导入的现有范围见[卡组与资料分享](SHARING.md)。

## 使用方式

1. 选择工作目录以外的备份目录。可以再选一个目录保存第二份副本。每个目标下的 `repeaty-<工作目录 UUID>` 子目录由 Repeaty 管理。
2. 手动创建完整备份，或启用定时备份并设置间隔及按小时、天、周、月保留的数量。各层按 UTC 时间桶选取最新一份，取并集；始终保留最新一份。自动备份需要桌面应用运行，关闭应用后不会由系统后台服务继续执行。
3. 选择已有备份预览，检查时间、数量及校验结果。可以按笔记或材料标题、文本内容搜索。查询只读取备份，不修改它。
4. 完整恢复时选择父目录。Repeaty 创建新的 `Repeaty-restored-<UUID>` 子目录，验证成功后把它加入“最近打开”。当前学习库保持打开；可以随后主动打开恢复的副本。
5. 从搜索结果恢复单个笔记或材料，会把接受过的文件与附件树导出到一个新的目录，供检查或重新导入。这不会把该笔记的调度或评分历史合并进当前库。需要保留完整历史时使用完整恢复。

列表只读取归档头部，不解包附件，显示“未完整校验”。选择预览、搜索或恢复时才校验完整内容。历史正文命中可查看摘要；单项恢复入口只针对该备份中的活跃或退役实体。搜索结果携带实体类型、ID、退役状态与内容摘要的恢复标识，避免同名路径或相同 ID 的不同类型恢复串用。

单项副本的相对附件以该实体已接受的不可变原件为准，原目录中尚未接受的图片或音频修改不会被误配到接受过的正文。一次选择的实体若要求同一路径对应不同正文或不同附件字节，会明确报冲突并取消该副本，不能静默覆盖。

备份目录、第二目标和自动备份策略属于当前设备配置。搬到另一台设备后，需要重新选择目标。恢复得到的新工作目录使用新的工作目录 UUID，因此也需要单独设置备份策略。

## 包含和排除的内容

完整备份保存以下数据：

- 活跃与退役的笔记、卡片及原有实体 ID、调度状态。
- 评分、专项练习、完整答题代码和结果、可用的历史检查点与撤销/重做记录。
- 学习材料、原件、旧版本、阅读位置、来源与发布映射。
- 未确认的制卡草稿、上传对象、学习库偏好。
- 已安装插件包、插件设置及工作目录内的插件私有文件。
- `notes/`、`sources/`、`assets/` 中的文件，包括尚未接受的外部编辑；接受过的内容对象和保留的被替换文件也独立保存。
- 附件回收站记录及尚未永久清除的对象。

不包含设备凭据、设备上的插件代码信任、最近目录列表、备份目标配置、窗口偏好、锁文件、临时 staging 文件或另一个完整备份目录。第三方插件自行写入其私有目录的数据会随插件数据备份；插件应通过宿主凭据 API 保存设备凭据。

恢复不会信任新设备上尚未信任的插件。插件包仍可被查看和管理，运行遵守原有设备信任流程。恢复时保留学习实体 ID；只有工作目录自身 UUID 会重新生成，以便原库与恢复副本安全共存。

## 一致性与失败处理

SQLite 使用 `VACUUM INTO` 生成一致快照，不直接复制正在使用的 `state.sqlite3` 与 WAL。应用自己的数据库和插件文件写入由工作目录会话互斥串行化。外部工作文件在导出前后检查清单、大小与 SHA-256；检测到编辑器并发保存会中止该次备份，保留原文件。

每份备份完成前都会验证 SQLite 完整性、外键、记录数量、内容对象和附件引用。缺少旧版本原件时不会发布一个看似成功的新备份。尚未恢复完成的文件发布意图会阻止导出，避免忽略 staging 中可能保留的原件。

导出先写同目标目录下的临时目录，完成后才以不覆盖既有文件的方式发布最终归档。旧备份只有在新备份验证成功后才可能按保留策略清理；目标不可用或校验失败时，不以失败结果删除旧副本。

分层保留先使用头部元数据选择各层代表，再完整校验所有将保留的代表；任一代表损坏时，该轮不删除旧备份。删除候选本身也必须通过完整校验，并保持文件身份、大小、修改时间与头部摘要不变。损坏备份不会因为占据某个时间层的名额而导致健康旧副本被清理。

恢复先解包到目标父目录中的私有临时目录，完整校验、核对预览时的摘要、重新打开验证后，再发布新目录。已有目标不会被覆盖；原库不关闭、不回写。取消和可捕获的失败会清理本次临时输出。进程被强制结束时可能留下 `.repeaty-backup-<UUID>` 临时目录；它不是完成的备份，不会被自动当作有效归档列出。

恢复预览与搜索需要临时磁盘空间来校验和读取快照。导出、校验与恢复按块流式处理，不把全部附件放入内存。取消在流式处理块和阶段边界检查；已经开始的 SQLite `VACUUM INTO` 会完成当前阶段后响应取消。

Windows 的目录刷盘保证遵循已有文件协议的 `FileOnly` 边界；原生 API 测试与故障注入不等同于物理断电、真实磁盘满、安装包或其他平台实机验收。

## 文件格式 v1

归档无压缩、无加密。结构为：

| 顺序 | 内容                                               |
| ---- | -------------------------------------------------- |
| 1    | 16 字节 ASCII magic：`REPEATY-SNAPSHOT`            |
| 2    | 8 字节 little-endian 无符号整数：manifest 的字节数 |
| 3    | UTF-8 JSON manifest                                |
| 4    | 按 manifest `files` 顺序连接的原始文件字节         |

Manifest 使用 `format: "repeaty-workspace-backup"` 和 `version: 1`，包含 `id`、`sourceWorkspaceId`、`createdAt`、`revision`、`totalBytes`、`counts`、`directories` 与 `files`。每个文件项为 `{path,size,sha256}`。整个归档的 SHA-256 由预览返回，恢复必须匹配该值。

目录列表摘要的 `verified` 为 `false`，全包 `sha256` 为空；`manifestSha256` 只标识规范化头部 JSON，不代表负载校验成功。完整校验后的摘要才返回 `verified: true` 与全包摘要。

允许的路径仅为 `workspace.json`、SQLite 快照 `.repeaty/state.sqlite3`，以及 `notes/`、`sources/`、`assets/`、`.repeaty/objects/`、`.repeaty/media/`、`.repeaty/retained/`、`.repeaty/plugins/`、`.repeaty/plugin-data/`。拒绝路径穿越、绝对路径、重复或大小写冲突、符号链接、重解析点、硬链接及平台保留路径。Manifest 最大 32 MiB，文件和目录合计最多 200,000 项，总内容最多 1 TiB，路径层级最多 64 层。

## 附件与数据库维护

普通评分不再自动删除上传对象，也不扫描插件私有正文。附件整理是用户主动执行的操作：预览检查当前内容、材料版本、历史、退役记录、草稿、持久撤销及插件引用，并核对文件现状。移入回收站保留字节；恢复标记不改变实体 ID；永久清除只对再次核对后仍可清理的对象执行。

数据库维护先检查 SQLite 完整性并显示数据库页数及可回收空间。用户执行整理后，运行 WAL 检查点与 `VACUUM`；它不会删除学习记录、插件数据或退役内容。
