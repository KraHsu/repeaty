# 工作目录中的 Markdown 与外部编辑

- 日期：2026-10-25
- 状态：M0 编解码与变更分类原型已实现；尚未接入真实工作目录，格式待平台保存与恢复验证后固定。
- 已确认要求：Markdown 外部编辑是工作目录模式首批必须实现的能力，不再作为可选后续增强。
- 上层方案：[工作目录模式与旧库迁移](WORKSPACE_MODE.md)。本文件细化正文格式、身份、文件变更与事务约定；具体编码需经 M0 样例验证后固定。

## 1. 各类数据的权威来源

| 数据                                                    | 权威来源                                        | SQLite 中允许保存什么                                                    |
| ------------------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------------ |
| 卡片笔记正文、题型、卡组引用、标签与插件题目数据        | `notes/` 中带 Repeaty 元数据的 Markdown         | 最近接受版本的投影、身份映射和历史版本引用，不作为第二份可独立修改的正文 |
| 可编辑阅读材料                                          | `sources/` 中的 Markdown / 文本及必要身份元数据 | 文档身份、当前接受版本、阅读安排和各版本的位置                           |
| 未确认制卡草稿正文                                      | `drafts/` 中的 Markdown                         | 队列、出处、确认事务与附件引用；未通过正式校验时不产生学习卡片           |
| 图片、音频等当前工作文件                                | `assets/` 中的文件                              | 媒体身份、路径、当前内容摘要与版本映射                                   |
| FSRS 状态、评分、练习、完整判题记录、生命周期、库内设置 | `state.sqlite3`                                 | 这些数据本身，不能删除后靠 Markdown 恢复                                 |
| 已接受的历史正文、来源快照与历史附件                    | `.repeaty/objects/` 的不可变对象及数据库引用    | 接受版本的头指针、出处关系与校验值                                       |
| 搜索、渲染与缩略图缓存                                  | `.repeaty/cache/`                               | 可重建的投影                                                             |

工作文件表达作者当前写下的内容，可能暂时不完整；「已接受版本」是通过身份、语法与引用校验后可用于学习的快照。外部文件尚未通过校验时保留其原字节，界面明确显示待处理状态，并继续使用已有有效版本。两者不是任意选择较新的一份正文。

索引损坏可以从已接受对象和工作文件重建。`state.sqlite3`、历史对象、事务日志和尚未接受的工作文件都不能当作缓存删除。目录整体复制必须包含 `.repeaty/`；只有 Markdown 文件不能恢复复习进度和历史。

## 2. 笔记文件格式草案

一条 Note 对应一个 Markdown 文件，而不是每张复习 Card 各存一份正文。双向卡的两张卡、挖空的多个编号继续共享同一笔记身份。

```markdown
---
repeaty:
  version: 1
  kind: note
  id: note-closure
  type: basic
  format: markdown
  deckId: deck-javascript
tags:
  - JavaScript
---

什么是闭包？

<!-- repeaty:answer -->

函数与其能够访问的词法环境的组合。
```

格式约定：

- 首个 frontmatter 块是结构化元数据，`repeaty` 命名空间声明托管类型与身份。正文之后出现的 `---`、标题、公式或代码围栏仍属于正文。
- Frontmatter 采用经过限制的安全 YAML / JSON 值模型，不执行标签、对象构造、别名展开或文件包含；限制深度和大小。未知的普通编辑器属性保留，不自动删除，也不授予运行能力。
- 默认答案边界是独占一行的 `<!-- repeaty:answer -->`。边界是笔记文件的结构分隔，先分题面和答案，再分别按 Markdown 或 plain 渲染，不使用任意标题或横线猜测答案。
- 分隔行前后的格式换行与正文原有换行必须可区分。编码器与解码器要能逐字恢复原题面 / 答案，包括空答案、首尾空行、CRLF、HTML 和未闭合代码围栏，不能为了输出美观执行 `trim()` 或 AST 重排。
- 答案边界可由 `repeaty.answerMarker` 指定受限标记，例如 `repeaty-answer-<随机标识>`。迁移时检查原题面和答案；若其中已有默认标记整行，包括代码示例中的字面标记，选择不冲突的标记并写入元数据，不改写原内容。发现多个声明边界则报歧义，禁止选第一处继续导入。
- 是否采用上述单文件分隔的最终编码，由 M0 的无损往返样例决定。若不能无损表示全部已支持正文，必须修改编码方案，不能放宽迁移核验来绕过。
- `format: plain` 保留旧纯文本语义。文件使用 Markdown 承载结构，不代表自动把旧纯文本卡改成 Markdown 渲染。
- 现有 Note schema 包含 `trim()` 等变换。新的文件正文需以原样保存、另行判断是否为空，不能把旧解析器或 `saveNote()` 当成无损文件编解码器。
- 已有 `frontMedia` / `backMedia` 通过显式元数据保存原媒体 ID 与库内路径，不为迁移而重复插入图片标记或改变题面文字。新写入的普通 Markdown 图片 / 音频引用也按库内路径识别并关联媒体身份。
- Card ID、调度、评分与作答历史不嵌入需要用户编辑的 Markdown。数据库保留 `(noteId, variant) → cardId` 的稳定映射，迁移保留原 Card ID。

应用创建文件时填写稳定 ID。未登记文件缺少身份时进入待登记列表，可以明确注册为新笔记；不得每次扫描都分配新身份。AI 和脚本可以按公开模板写文件，已有文件的 ID 必须保留，不需要 MCP 才能创建内容。

没有 Repeaty 标记的普通 Markdown 不自动变成复习卡片。未知文件、其他编辑器的配置和自定义属性也不自动删除。首先支持用任意编辑器修改 Repeaty 工作目录中的托管文件；现成 Obsidian 库的自动转换不作为这一格式的隐含承诺。

## 3. 身份和学习状态如何保持

| 外部操作                                           | 处理约定                                                                       |
| -------------------------------------------------- | ------------------------------------------------------------------------------ |
| 修改文字、格式、标签、附件，或移动到另一个已知卡组 | 接受新的内容版本，保留现有 Card ID、评分与调度，不自动重学                     |
| 重命名文件或移动目录                               | 按文件内的稳定 ID 关联；更新路径，不按文件名新建卡片                           |
| 复制文件并保留相同 ID                              | 将冲突身份列为待处理，保留双方文件与上一有效版本；不自动挑较新的文件           |
| 在原路径改写已登记 ID                              | 作为身份变更冲突处理，明确选择创建独立笔记或修正 ID；不静默重置进度            |
| basic 改成 reversed                                | 保留 forward 卡及进度，仅初始化新增 reverse 卡                                 |
| 新增挖空编号                                       | 为新增变体建立新 Card ID，已有编号保持原进度                                   |
| 删除 / 改名挖空编号，或删除一种方向                | 原变体退役，保留其身份、最后内容版本、调度与历史；相似文字不自动继承旧编号进度 |
| 删除文件                                           | 排除临时写入和重命名后，转为可恢复的停用状态；不立即清除历史和内容对象         |
| 恢复原文件 / 原编号                                | 默认恢复原身份与保留状态；永久删除或重置学习状态需单独明确操作                 |
| Markdown、元数据、卡组或附件引用不完整             | 保留文件并显示待处理原因，不清空旧正文、不创建半张正式卡片                     |

当前 Library v13 的变体集合与引用约束不能完整表达「当前正文已移除，但评分历史仍保留的退役卡片」。工作目录格式需要明确的 Card 生命周期和历史内容引用，不能直接复用删除旧卡、重建新卡的路径实现外部修改。

复习中的题面使用开始作答时的已接受内容版本。外部修改不能在用户作答中途悄悄换题。普通编辑可在提示后重载；评分需记录实际见到的内容版本。若变体已经退役或调度基线变化，先处理当前卡片状态，不把评分写给另一个身份。

## 4. 阅读材料与不可变出处

Markdown 材料在文件元数据中保留 Source ID；纯文本材料可以使用随文件保存的身份 sidecar，避免将 frontmatter 插入原文本。正文外的元数据不计入原文 UTF-16 选区。

新增 `SourceRevision`，把可编辑文档身份与不可变正文版本分开：

1. 第一次迁移时，每个旧 Source、media ID 和正文建立确定的初始版本映射，原 Source ID 与字节继续保留。
2. 外部修改正文时，Source ID 不变，生成新的不可变正文版本；现有摘录、制卡出处和草稿继续指向原版本，不将旧偏移套到新文本上。
3. 阅读安排仍归属文档；位置绑定具体版本。无法可靠映射到新正文时，新版本从头阅读，旧版位置保留，不能直接截断旧偏移后宣称定位成功。
4. 编辑摘录自身时，保留其旧的逐字摘录版本。新内容标记为由该版本编辑而来；不能沿用「当前正文等于父级原文范围」的旧断言。
5. 来源历史对象仍被摘录、卡片、草稿或检查点引用时不得回收。

这些语义需要工作目录专用 DTO / 适配。当前 Source / Excerpt schema 没有版本字段且校验逐字范围，不能用类型断言把新正文塞进旧记录。v13 的迁移输入保持原样；新关联只在新的工作目录中建立。

## 5. 文件变化的接收流程

```text
文件事件或重新扫描 → 读取稳定内容 → 校验身份 / 语法 / 引用
                  → 保存不可变内容版本 → 提交数据库投影与变更日志
                  → 更新界面和同步待发送状态
```

文件监听只是变化线索，不是唯一事实来源。启动、重新进入前台、监听溢出或手动刷新时要重新核对目录。监听失败不能让索引永久停留在旧内容；应明确显示状态并支持重新扫描。编辑器替换文件可能改变 inode 等监听对象，参见 [文件监听的局限](https://nodejs.org/api/fs.html#caveats)；这里不据此预先选定 Node 作为桌面监听实现。

逐项要求：

- 合并短时间重复事件，识别编辑器先写临时文件再替换目标的保存方式；读取期间仍变化的文件继续等待稳定。
- 按身份、内容摘要和版本去重，Repeaty 自己保存引起的事件不重复生成卡片或变更记录。mtime 与文件名不能作为唯一内容版本。
- 新增文件 / 附件到达顺序可以不同。未齐备的引用保留为待处理；其他独立、合法笔记仍可更新。
- 重命名、临时缺失和最终删除通过稳定扫描与身份关联区分。未知 sidecar 或原子替换的中间状态不产生永久删除。
- 解析失败时，不用数据库的旧副本自动覆盖外部文件，也不将空白的临时文件当成删除全部内容。
- 普通 Markdown 链接与附件路径必须留在工作目录允许范围内。符号链接、绝对路径和 `..` 不能用于跨目录读取；外部 URL 继续受现有渲染和原生链接策略约束。
- 外部 HTML 仍通过现有清理与样式隔离；frontmatter 中声明插件只表示数据，不能触发代码执行、自动判题、凭据读取或授权恢复。
- 附件修改也产生新版本。已接受内容的版本描述包含正文和实际使用的附件版本，不能只对 Markdown 字节计算一个摘要就忽略图片变化。

## 6. Repeaty 内部编辑、冲突与中断

Repeaty 内部编辑也写回同一 Markdown 工作文件，不在数据库里保留一条独立发展的正文。编辑器记录打开时的内容基线；接受文件变更和保存应用编辑都使用同一个协调器。

两侧都修改同一笔记时，优先保留版本，不能无提示最后写入覆盖。应用可在确认无冲突的情况下保存；冲突时保留外部文件和应用待保存版本，提供比较或另存。外部写入的 YAML 未知属性、换行和未修改正文不能因一次应用保存而被全量重排。

「写前检查摘要，再 rename」本身不是与非配合编辑器之间的强原子比较交换；SQLite 锁也锁不住普通编辑器。M0 需验证各平台保存目标旧版本再替换的原语，例如 [Windows ReplaceFile](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew) 和 [Linux rename 交换](https://man7.org/linux/man-pages/man2/rename.2.html)，并测试编辑器仍持有旧文件句柄的情形。未取得稳定内容或宿主不能验证安全替换时，应用保留目标文件并将新版本另存为冲突文件，不能用普通覆盖假装已经解决竞争。平台与编辑器的验证范围需要明确，不承诺控制任意第三方程序的文件写入。

跨文件 / 数据库的应用保存采用可恢复事务日志：

1. 保存前记录操作 ID、原内容版本、目标身份与预期路径，准备新正文、附件对象和要执行的数据库修改；所需恢复材料先持久保存。
2. 发布工作文件时保留实际被替换的版本，发现竞争即转为冲突，不继续覆盖。文件系统变化尚不等于该版本已被用于学习。
3. 在一个 SQLite 事务中提交接受版本、卡片变体 / 生命周期、媒体引用、检查点、变更日志及需要消费的制卡草稿。
4. 提交后完成日志并通知界面；重复扫描和重试沿用同一操作身份。

崩溃后按事务记录核对实际文件。文件已发布而数据库未提交时，要么补完同一次接受，要么将该修改标为待处理；不得直接拿旧数据库覆盖文件。文件又被外部编辑时，保留新的修改，原接受操作仍可从持久对象中辨认。尚未完成事务的文件不由另一个扫描过程独立登记。

草稿确认要预先记录 `draftId → noteId` 的同一次确认身份。正文文件发布与数据库提交之间的中断不能导致重复制卡，也不能提前消费尚未被正式接受的草稿。文件、数据库和事务日志不会形成一个天然的共同原子事务，这部分必须通过故障注入验证。

## 7. 迁移、备份与同步的影响

- 迁移在新暂存目录中生成 Markdown 包装和必要元数据，解码后的题面 / 答案、旧 ID、完整记录与附件字节必须与输入相符。先验证格式往返，再执行正式库迁移。
- 未完成草稿可以暂时没有合法答案；迁移到草稿文件不会将它们初始化成新学习卡片。LeetCode 完整提交历史继续结构化保存，不因 Markdown 模式丢失代码或结果。
- 首次打开迁移完成的目录时，文件与接受版本已经对应。扫描不能再产生一轮「新导入卡片」、重新计算到期或重复添加入门卡组。
- 内容工作文件与历史快照分开保存，不能将可编辑文件和不可变对象硬链接在一起。空间估算需包含两者及迁移暂存；同内容的历史对象可以去重，但不同媒体身份的可编辑文件不能因此意外绑成一个可变文件。
- 普通文字修改仍可投影到当前模型；退役卡片、版本化出处和编辑过的摘录可能超出 Library v13 / `.repeaty` v10 的表达能力。兼容导出必须说明这些范围，不能丢弃历史来伪造完整往返。完整目录及新格式的完整备份保留所有状态。
- 文件同步可以传输 Markdown 改动，但评分、完整历史和数据库冲突仍需要应用层协议；本轮不宣称把整个活跃目录放进任意网盘就获得了完整并发同步。
- 新增同步协议时，同步源内容与已接受变更要避免重复入队；离线外部编辑在下次打开或扫描后被接受，处理规则与本机编辑相同。

## 8. 首批验收样例

以下区分原型与真实目录验收；详见 [M0 验证记录](WORKSPACE_M0.md)。其余项目仍是 M0 / M1 / M2 门槛：

- [x] M0 脱敏原型的 Markdown 元数据与正文无损往返：中文、emoji、首尾空行、CRLF、HTML、公式、代码围栏、分隔标记字面量、plain、空答案和未知属性；已有正文编辑保留原元数据，元数据编辑器仍待实现。
- [ ] 正反面、双向和挖空文件的新增 / 修改；普通修改保留原评分与到期，新增编号仅创建新增卡，删除与恢复编号保留历史身份。
- [ ] 外部修改、移动、复制、错误修改 ID、短暂缺失、真实删除与恢复；重复扫描不重复建卡。
- [ ] 新文件未登记、错误 YAML、缺答案、卡组 / 附件尚未到达、未知插件；保留文件和上个有效学习版本。
- [ ] 应用与编辑器同时修改，临时文件替换、原地写入、旧文件句柄继续写入，及每个文件 / 数据库提交边界的崩溃恢复。
- [ ] 材料外部编辑后的旧版摘录、卡片出处、阅读位置与多级来源仍指向正确原文；编辑摘录不会伪装成逐字来源。
- [ ] 附件替换 / 删除与复习中的题面版本保持；在原题上作答不会被后台内容变化悄悄换题。
- [ ] MCP 草稿确认中断后只产生一条正式笔记；未完成文件不得消耗草稿或授予分享权限。
- [ ] Windows / macOS / Linux 的实际编辑器保存行为、重复 / 丢失文件事件、重新扫描和安全替换。

M0 首批的 Markdown 编解码、文件变更分类、变体与来源版本提议、只读旧库清点已通过脱敏单元测试。真实目录写入、停写协调器、跨文件事务和迁移器尚未实现；上面的实际保存、重启与恢复验收不能用纯函数结果代替。
