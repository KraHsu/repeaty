# 工作目录模式与旧库迁移方案

- 日期：2026-10-25
- 状态：设计草案；未实现，不改变 0.27.0 的存储、接口或数据。
- 基线：Repeaty 0.27.0，`4ebe2d3`。
- 本轮授权：制定工作目录与迁移方案。同步实现、收费服务及发布范围另行安排，不把本文件中的设计计为已完成功能。
- 相关决定：[ADR 015](adr/015-workspace-mode.md)。

## 1. 目标与本轮决定

Repeaty 的长期使用入口是「创建学习库 / 打开已有目录」。卡片、附件、复习进度、阅读材料、草稿和库内设置归属于这个目录；用户换电脑后可以打开完整副本继续学习。本地保存无需账户，也不等待网络。

用户已确认 **Markdown 外部编辑是首批必须实现的能力**。主方案改为 Markdown 承载可编辑正文与笔记元数据、SQLite 保存学习状态和事务信息，附件保存在目录中；正文不能继续以数据库为唯一来源。外部保存、重命名、身份冲突、变体变化和出处版本须与目录模式一起设计、实现和验收，详细规则见 [Markdown 与外部编辑](WORKSPACE_CONTENT_FORMAT.md)。

先完成目录自包含、原有能力适配和无损迁移，再开发同步。同步阶段仍保留客户端本地完整数据，通过后台传输变更连接其他设备。当前的上游 API 是远端学习库访问协议，不直接当作同步协议使用。

产品继续只有一个核心版本号。浏览器和 Tauri 是同一客户端的运行宿主，Rust 提供可选服务；内部目录格式、数据库和 API 的兼容标记不是另外的产品版本。

本方案保留 MIT 和现有功能的免费使用。自建、第三方同步和未来托管服务的费用政策不改变本地数据所有权；本轮不设计支付、订阅或商业版。

## 2. 当前代码中的数据清单

当前格式是 Library / JSON v13、IndexedDB v16、服务端 SQLite v10、API v11、`.repeaty` 容器 v10。这些是迁移输入的实际基线，不在文档阶段修改。

| 数据                                               | 0.27.0 中的位置                                         | 迁移要求                                           |
| -------------------------------------------------- | ------------------------------------------------------- | -------------------------------------------------- |
| 卡组、笔记、卡片、评分、常用搜索、练习、提交、材料 | IndexedDB `repeaty` 的实体表；账户模式为各账户的 SQLite | 保留原 ID、顺序、字段与引用                        |
| 图片、音频、不可变材料正文                         | IndexedDB `assets`；服务端 `assets` BLOB                | 保留原媒体 ID、MIME、名称、大小和字节              |
| 调度状态、暂停、暂缓、顽固卡、阅读安排与位置       | Card、Review、Source 等记录                             | 直接迁移，不重新评分或计算到期时间                 |
| 完整代码、判题结果和错误状态                       | 完整 Attempt 记录；界面通常只加载摘要                   | 读取完整记录，不能拿界面摘要替代                   |
| 自动 / 手动检查点与增量恢复历史                    | `checkpoints`、`history`；部分旧库还保留旧式备份        | 直接迁移时保留可恢复状态和所需附件                 |
| MCP 待确认制卡草稿及附件                           | 主 IndexedDB 的 `cardDrafts`，独立于 Library            | 单独迁移；现有 `.repeaty` 不包含它们               |
| LeetCode 未完成代码、累计用时、待查询提交          | 独立 IndexedDB `repeaty-leetcode-drafts` v1             | 按旧库作用域归属迁移，禁止自动再次提交             |
| 答题历史显示、顶部通知偏好                         | localStorage `repeaty.preferences.v1`                   | 按已知字段迁入库内偏好                             |
| 插件开关                                           | localStorage `repeaty.plugins.v1`                       | 保留开关与插件版本需求，不自动授予新权限           |
| 语言、LeetCode 站点选择                            | localStorage 的语言与站点键                             | 当前设备补充为库内偏好；来源未提供时明确记录默认值 |
| 上游地址、最近打开目录、窗口状态                   | 原生 `desktop.json` 等设备配置                          | 作为设备配置处理，不自动连接迁移来源的服务         |
| LeetCode Cookie、账户会话、MCP 密钥与分享授权      | 受保护的设备文件或进程内存                              | 不放入工作目录、不导出、不恢复授权                 |

代码依据：[数据模型](../src/core/model.ts)、[本地仓库](../src/core/storage.ts)、[账户仓库](../src/backend/repository.ts)、[服务端存储](../server/src/db.rs)、[备份容器](../src/core/archive.ts)、[草稿结构](../src/core/card-draft-data.ts)、[LeetCode 草稿](../src/plugins/leetcode/drafts.ts)、[偏好](../src/preferences.ts)、[插件偏好](../src/plugins/index.ts)。

两个现有入口不能直接作为完整迁移器：

- `createRepository().load()` 会升级旧库并创建检查点，不是只读检查入口。迁移前不能先用它打开原库再声称原库未变化。
- `rekeyBackup()` 会重新分配媒体 ID，以保护导入目标已有的快照。新建独立工作目录没有这项冲突，迁移应绕过重新编号，保留所有已有身份与出处关联。

## 3. 工作目录的使用约定

### 3.1 创建、打开、复制与关闭

1. 创建时选择一个空目录，在暂存位置建立并验证完整库后，才登记为可打开的学习库。
2. 打开时检查格式、身份、必要文件和写权限。找不到外接盘或原目录时显示位置不可用，不另建同名空库，也不因此产生删除记录。
3. 同一目录改名或移动仍是同一个学习库，身份由 `workspaceId` 决定，不取决于路径或目录名称。
4. 关闭学习库后，复制完整目录到另一台设备，保留 `workspaceId`，表示继续使用同一个库。通过「复制为独立学习库」才分配新 `workspaceId`；内部笔记和卡片 ID 无需重编号。
5. 第一阶段先支持关闭库、停止外部写入后复制完整目录，包含 Markdown、状态数据库及 `.repeaty/`。运行中搬迁需要一致的文件与数据库快照，并保留未接受修改和所有历史引用；该流程实现前提示先关闭写入者，不能承诺只复制 Markdown 或数据库即可恢复。
6. 最近目录列表可以保存在设备上，但删除该列表、重装客户端后，仍能通过选择目录找回全部学习状态。

### 3.2 数据与设备的边界

目录包含正式学习记录、完整作答历史、材料和附件、持久草稿、库内设置、插件设置及插件需求清单。可重建索引、缩略图与临时下载不构成唯一数据来源。

设备凭据留在原有受保护存储。迁移不顺便更换凭据存储机制，也不把现有权限保护描述成已实现的加密或系统钥匙串。新的设备需要重新登录和授权 MCP。

窗口位置、设备 ID、本机绝对路径、文件访问许可、最近目录、同步连接凭据属于设备。主题、快捷键、通知与插件偏好可以属于库；语言从库内偏好读取，未设置时使用设备默认值。不可在两个位置各维护一份可独立修改的权威设置。

插件清单记录 ID、版本、内容校验值与设置。官方内置插件仍由应用提供。旧部署编译进程序、又没有独立安装包的自定义插件，需要相同构建或重新安装；迁移报告必须列出这个依赖，原始插件题目与设置继续保留。第一阶段不新增插件市场或动态加载器。以后携带第三方插件包时，新设备的执行信任和原生权限也不能由目录内的标记自动授予。

### 3.3 写入者与格式兼容

- 同一设备上，同一 `workspaceId` 只允许一个 Repeaty 数据库写入会话，包括位于不同路径的同身份副本。其他窗口只读，或明确关闭前一个会话后接管。此锁不约束普通编辑器；外部文件并发由版本与冲突流程处理。
- 设备 ID 在设备上生成。复制目录后，新写入使用新设备的身份；已存在的变更 ID 不重建，避免同步重传被当作新操作。
- 未识别的目录格式拒绝写入。缺少必要文件、数据库身份与清单不一致时进入诊断 / 恢复流程，不初始化覆盖。
- 第一阶段使用本机文件系统。网络共享目录和多个设备同时操作同一 SQLite 文件不作为受支持的写入方式。

## 4. 存储格式：Markdown 正文与结构化学习状态

### 4.1 已确认的格式方向

| 方案                                             | 与需求的关系                                                      | 决定                         |
| ------------------------------------------------ | ----------------------------------------------------------------- | ---------------------------- |
| 仅在目录内保存 SQLite 和附件                     | 目录可搬迁，但普通编辑器不能直接修改正文                          | 不再作为主方案               |
| Markdown 正文 + SQLite 学习状态 + 不可变历史对象 | 正文可被编辑器、AI 和脚本直接修改；进度、历史和事务仍有结构化存储 | 首批主方案                   |
| 所有学习记录与事件也全部文件化，SQLite 仅作索引  | 更适合纯文件级合并，但需要另一套日志、事务和回收机制              | 后续按完整第三方同步需求评估 |

Markdown 是当前创作内容的来源；`state.sqlite3` 是调度、评分、练习、草稿流程和其他结构化状态的来源。数据库中的当前正文投影只有一个接受版本，不能脱离文件独立编辑。已接受的历史正文、来源快照和附件版本保存为不可变对象，以便在外部文件不完整或已删除时保留实际学习过的内容。

因此，只有明确的 `cache/` 可以重建清理；SQLite 和历史对象都不是可随意删除的缓存。Markdown 外部编辑的身份、格式、变更接收与保存恢复约定以 [内容格式草案](WORKSPACE_CONTENT_FORMAT.md) 为准。

### 4.2 目录布局草案

```text
我的学习库/
├── workspace.json                 # 不可变的格式标记与 workspaceId
├── notes/*.md                     # 可外部编辑的笔记正文与笔记元数据
├── sources/                       # Markdown / 文本材料及必要身份 sidecar
├── drafts/*.md                    # 未确认制卡草稿正文
├── assets/                        # 当前附件工作文件
├── state.sqlite3                  # 调度、评分、练习、身份、生命周期与事务
└── .repeaty/
    ├── objects/sha256/ab/<摘要>   # 不可变的已接受正文、出处和附件历史
    ├── transactions/             # 跨文件 / 数据库保存的恢复日志
    ├── plugins/                  # 可携带的插件资源；无执行信任或凭据
    ├── cache/                    # 可重建索引、缩略图
    └── migrations/<迁移ID>/       # 不含凭据的清单、核验结果和迁移回执
```

SQLite 使用 WAL 时，`state.sqlite3-wal` 和 `state.sqlite3-shm` 可能存在。不能在数据库运行时只取主文件作为完整副本；关闭连接或通过备份 API 生成一致性副本后再搬迁。WAL 的约束见 [SQLite 官方说明](https://www.sqlite.org/wal.html)。

`workspace.json` 的初始建议值：

```json
{
  "format": "repeaty-workspace",
  "version": 1,
  "id": "c1d61f7b-5c3f-4d53-918c-22b55d89d344"
}
```

数据库重复保存并校验目录身份。库内设置、阅读安排等结构化状态在数据库中维护；笔记正文和声明为可编辑的元数据在文件中维护，不再各维护第二份可独立修改的值。版本 1 是建议的目录格式，尚未被代码支持。

新的数据库需有独立 `application_id` 和兼容门槛。当前旧服务只按 `user_version <= 10` 判断是否可升级，因此不能给新格式设置一个会被旧服务误当作旧库的低版本值。原型建议使用 `application_id = 0x52505459`（RPTY）及 `user_version = 1001`，并验证 0.27.0 服务拒绝读写新格式；这些内部标记在格式评审后固定，不增加对外产品版本。

### 4.3 数据与事务

- 保留现有 Note、Card、Source、Review、Practice 等身份和业务语义；为内容版本、版本化出处、退役卡片及待处理文件增加明确的工作目录 DTO，不用类型断言绕过旧模型的约束。
- 普通文字、格式、标签与卡组修改不重置调度。新增变体创建新卡；移除的方向或挖空编号退役并保留历史。移动文件按稳定身份更新路径，复制同一身份的文件则作为冲突处理。
- 媒体记录保留原 ID、名称、类型、大小和时间，另建工作路径与不可变版本映射。迁移生成安全文件名，不直接拿任意旧 ID 或用户标题拼接路径；普通编辑器添加的路径也必须受工作目录边界限制。
- 当前可编辑文件与不可变历史对象不能硬链接。只对不可变对象按内容去重，不把不同媒体身份的可变工作文件意外合并；所有检查点、原文版本和草稿对历史附件的引用都计入保留范围。
- 纯评分、阅读安排等不修改正文的操作继续使用单个 SQLite 事务。涉及正文和数据库的操作通过持久事务日志与恢复流程协调，不能声称 SQLite 事务同时覆盖普通文件保存。
- 先持久保存待接受的正文 / 附件对象与恢复信息，再发布工作文件和数据库接受版本。崩溃后核对实际文件，外部新内容保留为已接受或待处理版本，禁止拿旧数据库静默覆盖。
- 制卡草稿的正式笔记身份在确认开始时确定；接受笔记、卡片状态、媒体引用、消费草稿和变更记录同事务提交，跨文件的中断按同一操作恢复，防止重复制卡。
- 文件缺失、错误 YAML、半写入与缺少附件不立即清空正式内容。监听不是唯一依据，启动、溢出恢复及手动重新扫描都要核对实际目录。
- 正常评分只写变化的状态记录，不重写 Markdown，也不触发全库解析；正文编辑只使受影响的内容与索引失效。

## 5. 客户端与同步边界

桌面继续加载安装包内的 Vue 界面。通过现有平台适配入口增加工作目录仓库，复用制卡、复习、阅读与插件界面；不改为加载服务器网页，也不创建私有桌面客户端。

仓库作用域从路径 / 上游账号描述扩展为稳定的 `workspaceId`，缓存和迟到请求绑定会话代次。切库时仍撤销临时 MCP 分享。现有草稿 schema 的 `scope` 只接受 `local:`，因此必须新增明确的工作目录草稿适配，不能直接换成新作用域字符串再交给旧解析器。

浏览器端是同一客户端的宿主适配。第一阶段保留现有 IndexedDB 使用方式与完整导出入口；不强迫网页用户安装后端。后续验证浏览器虚拟目录、文件访问权限及状态存储，再接入同一内容协议。浏览器是否能直接打开同一个本机目录、观察外部修改取决于权限和实现支持；需要重开或手动重新扫描的环境必须明确说明，不能仅凭桌面完成就宣称网页已支持。[浏览器文件访问说明](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access)。

工作目录保存协议为后续同步预留变更记录与事务 outbox：稳定的操作 ID、库 ID、设备 ID、设备序号、实体身份、已知基线 / 因果关联、操作种类和内容 / 附件版本。外部编辑通过相同的校验与接受流程进入变更日志，离线期间的修改在下次打开或扫描后接收；应用自身的文件事件不重复入队。未发送变更与数据库接受记录同事务保存；重复发送不能重复评分。复制目录时，既有操作保留原身份。

迁移形成一个已核验的初始状态。旧的评分和代码保留为历史事实，不能重新执行这些评分来生成初始调度。新的评分要记录其基线、结果、当时使用的调度参数与实际见到的内容版本；作答中途的外部修改不会悄悄替换题面。

并发编辑、删除与同一卡片的离线评分需要单独的同步决定。该阶段必须保留所有真实答题事实，不能用整库覆盖或时间戳较新的一份数据静默丢弃历史；也不能未经验证就把并发评分当作有先后顺序的两次复习。本文件不选定最终合并算法，不宣称 outbox 已经构成完整同步。

自建同步和未来第三方存储适配可以使用同一协议。Markdown 可以由文件工具传输与合并，但 SQLite 中的评分和其他状态仍有自己的同步要求。直接将整个活跃目录交给网盘多端覆盖，不属于本方案已实现的完整同步能力；若必须无需应用协议就并发合并全部学习状态，还需评估第 4.1 节的全文件化方案。

私有部署只保留认证、受信任的服务能力和部署覆盖，逐步使用公共的工作目录 / 同步接口。个人 IAM 会话与服务端插件凭据不随学习目录下发。第一阶段不自动迁移、部署或重构私有服务。

## 6. 迁移输入与完整性分级

| 输入                                       | 能恢复的范围                                           | 处理方式                                                            |
| ------------------------------------------ | ------------------------------------------------------ | ------------------------------------------------------------------- |
| 本机 IndexedDB v16，含辅助数据库与已知偏好 | 正式库、完整提交、媒体、持久草稿、检查点和当前设备偏好 | 首批直接迁移入口                                                    |
| 旧 IndexedDB                               | 取决于实际存在的表和数据格式                           | 原始快照只读提取，在副本上使用经过验证的旧格式转换                  |
| `.repeaty` v1–10                           | 容器实际包含的学习记录与附件                           | 复用现有读取 / 校验规则，导入新目录；没有的草稿、设置与检查点不补造 |
| 旧 JSON 备份或旧 Library                   | 输入中实际存在的内容；旧格式字段可能较少               | 用现有兼容转换作为基线，保留转换说明；不凭空补媒体或评分证据        |
| 开源账户服务 SQLite v10                    | 当前账户库中的记录、附件及检查点                       | 管理员生成一致性只读副本，或将来通过授权快照会话导出                |
| API v11 服务                               | 现有完整学习记录和媒体；没有跨请求固定快照保证         | 可用现有 `.repeaty` 导出作为输入；完整直接迁移需补充快照能力        |
| 私有单库部署                               | 经授权导出的学习记录与插件数据                         | 用相同模型转换器；凭据和身份服务配置留在部署端                      |

迁移报告分别记录「已迁移」「来源未提供」「需重新安装 / 登录」「阻止发布的错误」。不能因为正式库成功导入，就将草稿或设置标成已恢复；也不能把来源没有的数据记成丢失后自动补造。

一个来源生成一个独立工作目录。本地库与旧上游库分别迁移；本轮不做已有多个库的自动合并，不覆盖非空目标。

## 7. 迁移流程

### 7.1 状态与恢复点

```text
发现来源 → 预检 → 取得只读快照 → 提取与转换 → 写入暂存目录
         → 逐项核验 → 发布目录 → 选择启用 → 完成
```

每一步写入不含秘密的迁移日志：迁移 ID、来源类型 / 格式、来源快照指纹、目标库 ID、完成批次、文件摘要、计数、转换说明和核验结果。设备绝对路径与账户绑定放在设备诊断记录，不写入可同步的便携回执。

尚未取得快照的一次失败只能重新取快照。已经取得固定快照后才允许按批次恢复；恢复时重新校验它的指纹。来源变化意味着另一个输入，不能在原暂存库上混着继续。

### 7.2 预检

1. 列出实际可访问的旧本地库、辅助草稿库、手选备份或当前账户；不读取其他账户的数据库。
2. 检查目标目录为空、路径可写且不嵌套于原应用数据目录中；校验大小写、符号链接别名和已有库身份，防止指向源数据或目标外路径。
3. 估算新数据库、附件、暂存、快照及安全余量所需空间，列出旧源不会被删除。不能仅检查最终目录大小而忽略迁移期间的峰值。
4. 让旧客户端停止写入，关闭其他正在使用该来源的窗口；暂停新的评分、自动保存与插件提交。进程内锁或新客户端的广播无法约束不认识该协议的旧程序。
5. 展示可读取的数据范围、缺失能力、插件依赖、源修订号和目标路径。此时不改变原库的格式或默认入口。

### 7.3 取得一致性快照

**IndexedDB：** 使用无升级的只读打开方式，先确认数据库确实存在。主库的正式记录、元信息、历史与制卡草稿从同一一致性读取范围提取。跨批次必须核对来源修订号，不能跨文件写入等待时依赖一个会自动结束的 IDB 事务。辅助 LeetCode 草稿与偏好来自另一个事务 / 存储，必须在停止旧写入后单独捕获并复核，不能声称跨数据库天然原子。

取快照前后核对正式修订号，以及草稿、辅助库和偏好的内容指纹。出现变化则中止本次提取并重新取快照。前后指纹是变化检测，不能替代快照隔离；无法可靠停止辅助库或旧客户端写入时，直接迁移入口应拒绝宣称完整快照，改用已完成的备份文件并如实报告其范围。不存在的来源不当作一个需要添加入门卡组的空库。原库只读，原格式升级仅在快照副本上执行。

**SQLite：** 对目标账户的库使用 SQLite Online Backup API 或等价的一致性快照，核验完整性，再读取副本。不能复制正在运行的主文件而遗漏 WAL，也不在在线原库上执行当前 `Database::open()` 的升级流程。[SQLite 备份说明](https://www.sqlite.org/backup.html)。

**远端服务：** 当前 API v11 的修订检查不足以固定媒体、检查点和所有辅助数据的整个导出过程。第一阶段使用已有备份输入，或由管理员取得账户数据库快照。后续直接远端迁移需新增有账户隔离、有效期、固定快照和分批读取的导出会话；会话凭据不写入目标工作目录。未提供该能力的服务不能被标为完整直接迁移。

### 7.4 提取与转换

- 按实体分批处理；完整 Attempt 按现有 `readAttemptBatch` 的 128 条方式或等价的只读快照游标读取。正文和附件按流处理，不把所有媒体转换成 Base64 放入内存。
- 所有现有实体 ID、媒体 ID、创建 / 修改时间、顺序和关系保留。Note 正文和可编辑元数据输出为 Markdown，Card 身份映射和学习状态写入 SQLite。旧格式确实缺少身份时，采用有记录、可重复的转换映射，恢复迁移不能再次随机生成身份。
- 直接保留调度状态、原到期时间、学习日、历史评分、评分前状态、关联卡自动暂缓信息、练习评估与撤销所需字段。不开启 FSRS 重算，不把迁移当作新复习。
- Markdown 包装和答案边界与原内容分开编码，碰到原文中的分隔字面量时选择无冲突标记。反向解码必须恢复原题面 / 答案；不能因为加入元数据就重排 HTML、修补代码围栏、改变 plain 语义或重编号媒体。
- 材料正文、不可变快照、多级出处、UTF-16 选区、阅读位置和自适应安排一并转换。每个旧 Source / media ID 建立初始不可变版本映射，原引用增加明确的版本归属。原偏移指向解码后的正文，不包含新增 frontmatter。必要的旧格式变换必须单列，不能静默重渲染或规范化 Unicode 与换行。
- 制卡草稿正文迁入草稿 Markdown，保留 ID、接收顺序、未完成文字、独立上传附件与新库作用域；不要求未完成草稿通过正式卡片校验。无效的原出处保留为需修复状态，不能直接确认。MCP 密钥、选区分享与请求重放权限不恢复。
- LeetCode 草稿按照旧作用域映射到对应新库，保留多语言代码、计时、尝试次数、待查询提交编号及结果。恢复后可以继续查看或明确恢复查询，不能自动重发提交、重复评分或继续累加离线期间的作答用时。
- 偏好使用来源 / 字段白名单迁移，避免将历史服务访问密钥或插件凭据混入。不要扫描并删改正文中看起来像凭据的文本；区分依据是字段归属。
- 未知插件的原始题目和版本标记保留，打开时使用不可用提示。无法识别的新格式记录停止正式发布，原始输入保留用于诊断；不删掉记录来通过计数核验。
- 直接来源的可恢复检查点需要重建其恢复状态并保留引用附件。输入只是普通 `.repeaty` 或 JSON 时，应报告检查点未提供。当前 UI 的临时撤销栈、临时阅读轮次与授权状态不迁移；持久历史中的撤销证据仍保留。

### 7.5 暂存、验证与发布

在目标父目录的同一文件系统中创建带迁移 ID 的暂存目录。数据库明确标记为迁移中，应用不能把它登记为正常库。按有界批次生成 Markdown、附件工作文件、不可变对象与数据库，记录文件摘要和已接受版本，失败可以恢复，也可以保留诊断后由用户清理。空间估算包含工作文件与历史对象的副本，不能只计算单份附件。

核验通过后，确保所有输出 Markdown 可反向解码、路径 / 身份无冲突且内容接受版本对应，关闭数据库连接、完成所需 checkpoint 与文件持久化，写入完成回执，再将暂存目录原子改名为最终目录。不跨文件系统假定改名原子。完成目录发布后才更新当前设备的最近目录 / 活跃入口；入口更新失败时，新目录仍可手动打开，原入口不指向半成品。

迁移不会删除原库或改写原账户库。对于直接迁移，启用前再次检查已捕获的源状态与当前来源是否出现分叉；若仍有旧程序写入，停止自动切换并要求重新取得快照。对于备份文件或管理员提供的数据库副本，只承诺恢复输入快照时点，不承诺已经包含在线来源后来的修改，也不自动停用那个来源。

发布重试先查迁移回执；若目标确为同一次迁移、同一快照且重新核验通过，复用已经完成的目录，不再创建一份。其他非空目标仍拒绝覆盖。成功后留下原库位置和只读快照信息，旧客户端不会因此获得写入新格式的能力。

## 8. 无损核验与回滚

### 8.1 成功必须满足的条件

- 九类实体、草稿与检查点逐项计数相符；比较 ID 集合、记录顺序和规范化后的完整记录，而非只比较页面上的卡片数量。生成的 Markdown 反向解码与原记录相符，第一次扫描不重复导入、评分或加入入门卡组。
- 调度和阅读状态逐字段一致，保留浮点用时精度、时间字符串及原学习日。导入后不新增评分、代码提交或阅读反馈。
- 逐个核对附件 ID → 内容映射、MIME、长度及 SHA-256；草稿附件与恢复检查点引用也参与检查。
- 复核所有记录引用、卡片变体、材料层级与 UTF-16 选区所指向的初始不可变版本。检查正文与附件的接受版本关系，不能只检查数据库外键。
- 完整判题代码与错误正文均已迁移，界面摘要数量不能替代正文核验。
- 迁移后的 SQLite 完整性、约束和工作目录身份检查通过；关闭并重开后再次读取核验。
- 隐藏 / 缺失插件的数据仍可导出。凭据、会话和授权没有进入便携输出；原设备的凭据文件保持原样。
- 空库保持空库，用户删除过的入门内容不重新加入。迁移不会触发默认入门初始化。

记录指纹采用规范化后的稳定编码，保留数组顺序和数值语义；附件单独比较原始字节。必要旧格式转换前后的差异另列，不用一个重新生成的指纹掩盖丢字段。指纹规则与测试样例在迁移器实施前固定。

### 8.2 失败与中断

| 情况                           | 结果与恢复                                                               |
| ------------------------------ | ------------------------------------------------------------------------ |
| 预检、读取、格式或引用校验失败 | 原库不变，目标未启用；报告具体记录 / 附件和原因                          |
| 写附件或批次中断、磁盘写满     | 暂存库不发布；校验固定输入后恢复，或清理此次暂存目录                     |
| 原库在快照期间继续变化         | 本次快照无效，重新取得，不拼接两个修订的数据                             |
| 发布目录之前崩溃               | 继续使用原库，暂存目录带恢复标记                                         |
| 目录发布成功、设备入口更新失败 | 新目录完整可打开，原入口仍可用；按迁移 ID 识别结果，不重复创建           |
| 新库已开始使用后要求回退       | 先保留新库完整副本；旧源只是迁移时点的数据，不能直接覆盖新产生的学习记录 |
| 复制缺文件或遇到较新格式       | 拒绝写入并提供诊断；不创建空库替代                                       |

0.27.0 的 `.repeaty` 仍是兼容学习数据导出，不升级宣传为包含草稿、插件和设置的全工作目录备份。退役卡片、版本化出处及修改过的摘录可能超出 v13 的表达能力；不能删掉历史或偷偷改写身份来通过旧格式校验。回退需要旧客户端可读的备份时，明确列出不能表示的数据并保留完整新目录，兼容导出的具体投影需另行验证。

目录本身也不是独立备份。应用内检查点与主库位于同一位置，仍需要用户保存一致性副本到其他介质。

## 9. 实施顺序与验收

按一名开发者安排顺序，不提前并行建设同步服务、插件市场或计费系统。每阶段在一个功能分支集中实现、测试与文档，阶段完整后再提交一个 PR。

| 阶段                   | 交付                                                                                 | 通过条件                                                                     |
| ---------------------- | ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| M0：内容格式与来源样例 | Markdown 编解码、身份 / 变体 / 来源版本规则、文件变更分类与旧源只读清点              | 所有代表正文无损往返；不升级旧库；安全替换和跨文件恢复方案有平台原型证据     |
| M1：桌面目录与外部编辑 | 创建 / 打开 / 关闭目录、Markdown 工作文件、接受版本、SQLite 状态、文件监听与重新扫描 | 在外部修改、移动和恢复文件后进度保留；冲突、错误保存、实际重启和中断恢复通过 |
| M2：迁移器             | 最新本地库、草稿、偏好、现有备份与服务端快照生成可外部编辑的新目录                   | 下列迁移矩阵通过，原库未改写；初次扫描不重复制卡，来源不完整与失败报告可区分 |
| M3：客户端收敛         | 同一内容协议与工作目录接口整理平台适配；验证浏览器虚拟目录 / 本机文件能力            | 静态网页继续可用，权限、重新扫描和格式兼容经过实际验证；不维护第二套业务前端 |
| M4：同步设计与实现     | 内容与结构化状态的并发修改、删除、评分、草稿同步范围、版本保留与访问控制             | 离线文件编辑、重复传输、两端评分及冲突恢复通过；服务不替换本地数据源         |
| M5：部署适配           | 私有认证与受信任的服务能力接入公共接口                                               | 通用客户端不含私有身份逻辑，旧部署可独立回退，凭据边界保留                   |

M0 的首项工程验证改为**仅对脱敏样例运行的 Markdown 编解码与文件变更分类原型**，同时建立只读旧库清点与快照协议。先证明格式无损、身份稳定、外部保存可辨认、来源清点不漏代码与草稿，再建设真实目录写入和迁移；不先上线自动迁移按钮。

建议的验收矩阵，全部尚待实施：

- [ ] 0.27.0 完整本地库、已发布旧版本代表样例、空库与删除入门卡组的库。
- [ ] 旧 `.repeaty` / JSON 样例，明确缺失草稿与检查点的报告。
- [ ] Markdown 的中文、emoji、首尾空白、CRLF、HTML、公式、未闭合代码围栏、答案标记字面量、plain 与未知属性的无损往返。
- [ ] 外部修改、改名、移动、复制、重复 ID、缺答案、半写入、删除 / 恢复和重新扫描；普通修改不重置进度，新增 / 退役变体保留正确身份。
- [ ] 编辑器与应用同时修改、临时文件替换、旧句柄继续写入及文件 / 数据库边界崩溃；草稿确认不重复制卡。
- [ ] 材料更新后，旧摘录、制卡出处、阅读位置和多级来源仍指向正确版本；编辑摘录不会冒充逐字范围。
- [ ] 1,000 / 10,000 张卡、长文本与合计 128 MiB 媒体；沿用现有单文件约束，不顺便扩容格式。
- [ ] 双向、挖空、未知插件、完整 LeetCode 记录、未结束草稿及 MCP 独立附件。
- [ ] 公开账户隔离、旧 API 能力不足提示、重复迁移及多库 ID 相同但作用域不同。
- [ ] 磁盘写满、只读目录、媒体损坏、源修订变化和恢复后再验证。
- [ ] Windows / macOS / Linux 的中文、大小写、保留名称、符号链接别名、锁、实际编辑器行为与原子发布。
- [ ] 目录改名、跨盘复制、新设备身份、不兼容客户端拒写及旧格式不能表达的新历史的报告。
- [ ] 本地保存不依赖网络；评分不重写正文或全库解析，批量外部编辑仅更新受影响内容，记录 0.27.0 基线与新路径的原始性能结果。

细化的内容验收见 [Markdown 与外部编辑](WORKSPACE_CONTENT_FORMAT.md#8-首批验收样例)。性能预算在 M0 基准后确定，不把未运行的测试或目标值写成已达到的指标。

## 10. 发布与后续确认

这是一项新的存储与迁移设计，尚未被确定纳入 v1.0.0。原有 [发布清单](RELEASE_1_0.md) 继续记录现有发布门槛，不能因为方案完成就勾选功能或迁移验收。

已确认 Markdown 外部编辑属于首批必要条件，M0 / M1 / M2 的内容格式、目录原型与迁移都按此执行，不再询问是否纳入。

其余设计门槛：

1. 在 M0 固定无损 Markdown 编码、版本化出处、退役卡片与跨文件保存 / 恢复协议，取得平台原型证据。
2. 是否还要求任意第三方文件同步工具并发合并全部学习状态；Markdown 文件可编辑不等于结构化学习数据库已经可并发覆盖。
3. 工作目录模式安排在哪个发布阶段；本轮不预先指定 0.28.0、v1.0.0 或完成日期。

同步服务、端到端加密方案、第三方同步适配和官方托管收费留在后续单独设计中，不是本轮迁移器的隐含前置工程。
